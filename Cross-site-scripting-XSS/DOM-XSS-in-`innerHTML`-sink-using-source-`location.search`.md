# [DOM XSS in `innerHTML` sink using source `location.search`](https://portswigger.net/web-security/cross-site-scripting/dom-based/lab-innerhtml-sink)

## **`الهدف`**
قم بتنفيذ هجوم `XSS` يستدعي دالة `alert`.
## **`خطوات الحل`**
نقوم بحقن الأمر التالي فى خانة البحث ونضغط `Search` لننتهي من حل اللاب.
```html
<img src=1 onerror=alert(1)>
```
## **`ترقيع الثغرة`**
يجب التوقف عن تمرير المدخلات القادمة من المستخدم مثل معلم البحث `search` عبر رابط الصفحة `location.search` مباشرة إلى مصبات غير آمنة `Sinks` مثل `document.write` والتي تقوم بدمج البيانات كأكواد `Raw HTML` وتسمح للمهاجم بحقن وسوم جديدة داخل الصفحة، واستبدالها بواجهات `DOM` الآمنة التي تعالج العناصر برمجياً دون تنفيذها كأكواد.

ويجب تعقيم أو ترميز أي بيانات ديناميكية يتم استخراجها من الرابط قبل تمريرها أو دمجها في الصفحة، وذلك لضمان تحويل أي رموز خاصة `Special Characters` مثل الأقواس `>` و `<` أو علامات التنصيص إلى كيانات برمجية `HTML Entities` لا يمكن للمتصفح تفسيرها كـ `Payload` خبيث يهدف لإنشاء وسوم خارجية مثل `<img>`.

وبما أن الهدف هنا هو مجرد عرض كلمة البحث المدخلة في مربع البحث داخل الصفحة في واجهة المستخدم `Frontend`، فيجب على المبرمجين الاعتماد على خصائص آمنة مثل `textContent` والتي تتعامل مع المدخلات كنص عادي `Plain Text` فقط، وتمنع تفعيل أي وسم `Tag` خبيث يتم حقنه مثل `<script>` أو `<img>`.

وكطبقة حماية إضافية `Defense in Depth`، يجب على السيرفر إرسال ترويسة سياسة أمان المحتوى `CSP` صارمة تمنع تنفيذ أكواد `JS` المدمجة `Inline Scripts` أو المنفذة عبر أحداث غير آمنة مثل `onerror`، فحتى لو فشل المطور في تأمين الكود برمجياً ونجح المهاجم في حقن الكود الخبيث، سيتدخل المتصفح ويمنع تنفيذ الـ `alert`.
